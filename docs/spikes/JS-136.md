# JS-136 — Kokugo skill map + skill review queue (spike result)

- Date: 2026-08-04
- Ticket: JS-136
- Status: **adopt** (thin implementation shipped with this spike)
- Related: ADR-0005; JS-131/132 progress store; JS-135 unit pack 2

## Investigation scope

How should Track B surface **skill-level progress** and a **weak-skill review queue** without collapsing into cloze SRS (`QuizContentType` / `next_due_at`)?

Done-when:

1. Skill progress can be derived from existing learner state + L1 unit JSON.
2. Recommendation: schema / API / UI shape with migration needs called out.
3. Review queue does not write cloze due dates or reuse quiz SRS tables.

## Angles (main-thread)

| Angle | Question | Finding |
|-------|----------|---------|
| A — Data already present | Do we need a new SQLite skill table? | **No for v1.** Tasks carry `skill`; attempts store `task_id` + `correct`; artifacts cover writing skills. Join at read time. |
| B — API shape | Separate endpoint vs inflate unit list? | **`GET /api/kokugo/skills`** keeps unit list cheap and makes the skill product surface explicit. |
| C — Review vs SRS | Can we reuse cloze due? | **Must not.** North star is full kokugo cycles + skill dimensions (ADR-0005). Review queue = incomplete units that exercise weak/unseen skills. |

## Findings

### What already exists

- `KokugoSkill` enum on each task (`reading.predict` … `writing.revision`).
- `kokugo_task_attempt(unit_key, task_id, correct, …)` — no denormalized skill column.
- `kokugo_artifact` rev0/rev1 for writing.claim-reason / writing.revision.
- Unit completion is cycle-based, not skill-based.

### Aggregation rules (v1)

| Signal | Rule |
|--------|------|
| Latest attempt | Per `(unit_key, task_id)`, highest `id` wins |
| Graded accuracy | Only attempts with non-null `correct` |
| `reading.predict` | Ungraded → `practiced` if any attempt, else `unseen` |
| Writing | Non-empty rev0 → claim-reason practiced; rev1 → revision graded by checklist-all-true |
| Status | `unseen` / `practiced` / `weak` (acc &lt; 0.6) / `strong` (graded ≥ 2 and acc ≥ 0.8) |
| Review queue | Incomplete units covering weak or unseen skills; score by skill hit count; cap 5 |

### Non-goals (v1)

- No migration / no `skill` column on attempts.
- No cloze SRS due dates for kokugo skills.
- No static IndexedDB skill map (JS-018 / JS-141 still separate).
- No multi-tenant ownership (same audience-of-one exception as progress).

## Recommendation

**Adopt read-time aggregation + dedicated skills endpoint + list-view UI.**

Shipped with this result:

- `server/internal/kokugo/skills.go` — pure aggregation
- `GET /api/kokugo/skills`
- `store.ListAllKokugoTaskAttempts` / `ListAllKokugoArtifacts`
- `KokugoTab` skill map panel + weak-skill review buttons

## Pilot walkthrough

1. Complete or fail tasks on any e5-6 unit via local API.
2. `GET /api/kokugo/skills` → six skills with labels + statuses; `review_queue` lists incomplete units for weak/unseen skills.
3. 国語教室 list view shows 技能マップ; review buttons open the recommended unit (`aria-label: 復習ユニット: …`).

## Open risks

| Risk | Mitigation |
|------|------------|
| Corpus grows → skills endpoint loads every unit JSON | Acceptable at &lt;20 units; later cache skill index in process memory |
| Writing skill “correct” is checklist self-report | Honest for v1; LLM quality scoring remains M4-deferred |
| Predict always “practiced” after one click | By design (ungraded priming) |
